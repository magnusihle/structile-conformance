ARC-009, SEC-007, SEC-008 and OSS-003. Catalog contract (`verification/test-catalog.json`,
unamended):

> `platform-conformance run supply-chain --frozen-lockfile --reproducible --verify-signatures`
> — environment "Clean builders; registry proxy; malicious dependency fixtures"; oracle
> "Containers satisfy runtime policy; builds are reproducible; secrets/high findings/unknown
> licenses fail; SBOM/notices complete; source/package/image signatures and provenance verify."
> Evidence artifacts: `container-policy.json`, `sbom.spdx.json`, `license-report.json`,
> `scan-report.json`, `provenance.json`.

The protected runner is `node:24.19.0-alpine` with `docker-cli` and `git`, dispatched with
`--network none`. There is no scanner, no registry and no vulnerability database in it, and no
`.github/workflows/release-signing*.yml` exists in any governed repository yet — a filename
pattern core's `policies/agent/protected-paths.json` lists as protected, and agents are denied
`sign-evidence` besides. So the oracle is
split clause by clause below, and every clause is labelled with what it actually does. **No
clause emits a zero it did not measure.**

## The signature clause: absence asserted, not assumed

At v0.2 nothing is published, so there is no signature to verify. A suite that reported "0
signature failures" here would be lying by construction. Instead the suite asserts *why* nothing
is published and fails closed the moment that stops being true:

- every workspace manifest is `private: true` with no `publishConfig` (14 inspected),
- no release tag matching `v*` exists,
- no workflow publishes (`npm publish`, `docker push`, `actions/attest`, `cosign sign`),
- no signed release is declared at `delivery/release-manifest.json` + `.sig` +
  `delivery/release-signing.pub`.

If any of the first three opens **without a verified release**, `auditPublicationSurface` emits
`publication-without-provenance`, `release-tag-without-provenance` or
`publishing-workflow-without-provenance` and the suite fails. This is the distinction that keeps
the clause from being vacuous: it separates *nothing published yet* from *published but unsigned*.

`verifyDeclaredRelease` is the code path that will run against a real release, and presence is
never accepted as proof — only a detached signature that verifies over the manifest's exact bytes
sets `verified: true`. Because the candidate declares no release, that path is qualified end to
end against synthesized release directories, and the qualification asserts both halves: the
verification verdict *and* that a rejected release leaves the publication finding standing.

| Synthesized release | `verified` | publication findings left standing |
| --- | --- | --- |
| valid signature | `true` | 0 |
| tampered manifest | `false` | 1 |
| truncated signature | `false` | 1 |
| empty signature | `false` | 1 |
| foreign key | `false` | 1 |
| manifest with no signature at all | `false` (and `present: true`) | 1 |
| manifest that declares no candidate or artifacts | `false` | 1 |

Each row's finding count is measured against a surface with one workspace made publishable. The
real candidate's surface is already clean, so counting findings against it would record a zero
that proves nothing about whether the release was rejected — an earlier draft did exactly that
for the last row and reported 0 where this table said 1.

The release paths above are a convention this suite declares, not one the catalog names. If the
human's signing design lands them elsewhere, the three constants at the top of
`src/supply-chain-audit.ts` are the only thing that changes.

## Design: findings, not throws

Every audit is a pure function returning `Finding[]`, so the identical audit runs over the real
candidate (the control, which must return `[]`) and over a synthesized mutant (which must return
the expected code). A suite that only asserts "the candidate passes" cannot distinguish a working
audit from one that never fires — the mutation lesson from the SPEC-002 and PKG-001 re-cuts,
where a mutation that failed to apply masqueraded as a pass. Here `assertDetects` fails if the
control already carries the code it is about to look for, so a mutant can never be credited for a
pre-existing finding.

Mutants are synthesized in memory or under `artifactDir`. Nothing is written to
`verification/fixtures/**`.

## Limits, and what remains

1. **No vulnerability scan.** Offline. Needs a scanner and a pinned advisory database in the
   runner image. That is a `Containerfile` change: conformance infrastructure, human-authored by
   convention (`AGENTS.md` plus review) rather than by a protected-path rule — this repository
   has no `policies/agent/**` at all — and changing it changes the attested runner digest every
   piece of G0 evidence is bound to. **Follow-up.**
2. **No real signature verification.** Needs a release-signing workflow to exist first
   (`release-signing*.yml` is protected). The verification logic is qualified and fails closed;
   what is missing is a real signed artifact to point it at. **Follow-up**, in the same shape as
   DEL-001's `verify-mechanical.mjs` dependency.
3. **Container policy is read off the build recipe, not off a built image.** A live image-config
   inspection would need the docker daemon; DEV-001 already starts the real stack and inspects
   image digests, so the two suites meet in the middle. A protected dispatch of both is the
   check that closes it.
4. **`--frozen-lockfile` here means pinned and integrity-complete, not `npm ci`'s full
   semantics.** It does not yet verify that the lockfile *agrees* with the manifests — that a
   dependency added to a package.json was actually locked. The lockfile mirrors each workspace's
   dependency block, so the comparison is exact and offline; it is a **follow-up** micro-task
   rather than part of this change, which would have pushed the pull request past the DEL-002
   ceiling.
5. **The reproducibility check deletes and rebuilds the candidate's `dist` trees.** Every other
   candidate-dependent suite rebuilds what it needs, so a crash between the delete and the
   rebuild is recoverable, but it is not a read-only probe and is called out here rather than
   discovered.

## localUnsigned / informative statement

Every run above is local and informative. `measurements.localUnsigned: true` and
`provenance.workflowIdentity: local-unsigned/not-release-evidence` are correct and expected;
they read otherwise only when the protected G1 workflow runs this suite against a pinned
candidate with the attested runner image. A passing local run means the implementation looks
right. It is not evidence, and SEC-005 supports no requirement or gate claim until a protected
dispatch says so.
