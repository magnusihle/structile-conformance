## Negative mutants

Built in a throwaway, detached-HEAD worktree of core pinned to
`653471d73f2352a77f2cf2ef2856f6f9e17873d1` (`git worktree add ... 653471d7... --detach`),
`npm ci --ignore-scripts` once, then one mutation at a time in
`packages/capability-sdk/src/{validation,execution-gate}.ts`, rebuilt with
`tsc -p packages/capability-sdk/tsconfig.json`, rerun, then reverted (`git checkout --`) before
the next mutant. Worktree removed with `git worktree remove --force` after all three.

**Mutant 1 — declaration validation dropped.** `validateActionDeclaration`: removed the
`for (const field of ACTION_FIELDS) { if (value[field] === undefined) violations.push(...) }`
required-field loop entirely, so a declaration missing any required field (`id`, `version`,
`scope`, `preview`, etc.) is no longer refused.

```
{"testId":"ACT-001","status":"failed","exitCode":1, ...}
measurements.error: "missing:id was accepted but must be rejected"
```

Fails for the asserted reason: the suite's `missing:<field>` probes delete one required field
at a time from an otherwise-valid declaration and expect rejection; with the check removed the
incomplete declaration validates, and `assertDiscriminates` reports the poisoned case was
accepted rather than rejected.

**Mutant 2 — forbidden scope accepted.** `validateActionDeclaration`'s scope-entry loop:
removed the `if (FORBIDDEN_SCOPE_KINDS.includes(entry.kind.toLowerCase())) { violations.push(...) }
else if (entry.kind !== "resource" && entry.kind !== "record") { violations.push(...) }` branch
entirely, so a scope naming `code`, `sql`, `network` or `infrastructure` is no longer refused.

```
{"testId":"ACT-001","status":"failed","exitCode":1, ...}
measurements.error: "scope:code was accepted but must be rejected"
```

Fails for the asserted reason: the suite's forbidden-scope loop asserts each of
`code`/`sql`/`network`/`infrastructure` is discriminated against an otherwise-valid control;
with the check disabled, the `scope:code` poisoned declaration (an `eval` scope value)
validates cleanly and the first forbidden-scope probe fails.

**Mutant 3 — execute endpoint prematurely available.** `execution-gate.ts`: flipped
`ACTION_EXECUTION_ENABLED` from `false` to `true` and replaced `assertExecutionDisabled`'s body
(`throw new CapabilityContractError("EXECUTION_DISABLED", [...])`) with a silent no-op, so the
execution gate no longer reports itself as closed and no longer throws when probed.

```
{"testId":"ACT-001","status":"failed","exitCode":1, ...}
measurements.error: "ACT-001: action execution must remain disabled at G1\n\ntrue !== false\n"
```

Fails for the asserted reason: the suite's first assertion after importing the SDK,
`assert.equal(sdk.ACTION_EXECUTION_ENABLED, false, ...)`, fails directly on the flipped
constant, before the gate's throwing behaviour is even probed — a strictly stronger failure
than the intended `assertRejects` mismatch it would also have produced.

Each mutant targets a distinct ACT-001 assertion class (required-field enforcement, forbidden
scope rejection, execution-gate closure) and was confirmed to fail specifically on the
mechanism exercising that class, not incidentally elsewhere.
