## Negative mutants

Built in a throwaway, detached-HEAD worktree of core pinned to
`653471d73f2352a77f2cf2ef2856f6f9e17873d1` (`git worktree add ... 653471d7... --detach`),
`npm ci --ignore-scripts` once, then one mutation at a time under `packages/capability-sdk/src`,
rerun via the suite CLI (no separate `tsc` invocation needed — `buildAndImport` rebuilds the
package as part of the suite run), then reverted (`git checkout --`) before the next mutant.
Worktree removed with `git worktree remove --force` after all three.

The reference adapters (`fixtures/capability/adapters/{node,python,go}`) are standalone
implementations that read only `contract.json` and `corpus.json` — none imports
`@structile/capability-sdk` — so the candidate does not host adapter logic and an
adapter-disagreement mutant is not reachable from candidate-side changes. All three mutants
below instead target distinct SDK-level assertions the suite makes directly against the
candidate's `@structile/capability-sdk` package, per the task's fallback instruction.

**Mutant 1 — version negotiation accepts a bad major.** `protocol.ts`,
`negotiateProtocolVersion`: removed the `.filter((major) => supported.includes(major))` step
from the offered-majors pipeline, so any integer major offered (including one absent from
`SUPPORTED_PROTOCOL_VERSIONS`) is accepted as the negotiated version instead of being refused.

```
{"testId":"CAP-001","status":"failed","exitCode":1, ...}
measurements.error: "negotiate:unsupported was accepted but must be rejected"
```

Fails for the asserted reason: the suite's `assertDiscriminates` call pairs a control offer
(the SDK's own supported major) against a poison offer (`major: 999`) and expects only the
poison to throw `CapabilityContractError`; with the filter removed, `negotiateProtocolVersion`
accepts major 999 instead of throwing, and the discriminator reports the poisoned case was
accepted rather than rejected.

**Mutant 2 — unsigned manifest accepted.** `validation.ts`, `validateCapabilityManifest`:
weakened the signature check from `typeof value.signature !== "string" || value.signature.length
=== 0` to `typeof value.signature !== "string"`, so a manifest carrying an empty-string
signature is no longer refused. (A first attempt removing the required-manifest-keys check
instead was reverted: every `MANIFEST_KEYS` entry is redundantly re-validated by the
array/shape checks further down the same function, so that mutation produced no observable
failure — a non-viable mutant, not a suite gap, since the suite's `expectationMismatches`
measurement would have caught a genuine acceptance of a key-missing manifest had one occurred.)

```
{"testId":"CAP-001","status":"failed","exitCode":1, ...}
measurements.error: "sdk:manifest.unsigned-empty was accepted but must be rejected"
```

Fails for the asserted reason: the suite iterates every `manifest`-kind corpus case through
`sdk.validateCapabilityManifest` and asserts each non-accepted case rejects with
`CapabilityContractError`; the protected corpus's `manifest.unsigned-empty` case carries
`signature: ""`, and with the length check dropped, `validateCapabilityManifest` returns
successfully instead of throwing `UNSIGNED_MANIFEST`.

**Mutant 3 — database/DOM shortcut introduced.** `index.ts`: added a comment line
`// mutant probe: postgres://localhost/structile` above the package's barrel exports — no
functional change, purely a string literal matching the ARC-006 forbidden-pattern scan.

```
{"testId":"CAP-001","status":"failed","exitCode":1, ...}
measurements.error: "the capability SDK must not reach a database or the DOM directly
+ actual - expected

+ [
+   {
+     path: 'src/index.ts',
+     pattern: '/postgres(?:ql)?:\\/\\//i'
+   }
+ ]
- []"
```

Fails for the asserted reason: the suite scans every `packages/capability-sdk/src/**/*.ts` file
for a fixed set of database/DOM patterns (including `postgres(?:ql)?://`) and asserts the
`shortcuts` list is empty; the injected literal is a byte-for-byte match for that pattern and is
correctly flagged in `src/index.ts`.

Each mutant targets a distinct CAP-001 assertion class (protocol version negotiation, manifest
signature enforcement, database/DOM shortcut prohibition) and was confirmed to fail specifically
on the mechanism exercising that class, not incidentally elsewhere.
