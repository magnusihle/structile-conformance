# PKG-001 qualification — package-matrix

**This is a rewrite for the released-majors amendment (planning#1), not a port.** The salvage
suite at `origin/g1/protected-suites:src/suites-g1b.ts` L213–301 (`packageMatrix`) asserted
unconditionally that the published specification compatibility matrix names two installable
schema majors ("a single supported major cannot demonstrate N/N-1 distribution"), which
presupposes a released spec major 2 that does not exist. It also invoked the CLI with
`--schema current,previous`. The amended catalog entry (`verification/test-catalog.json`,
PKG-001) is authoritative and reads:

> `platform-conformance run package-matrix --schema released --frozen-lockfile` — All products
> use exact compatible versions; every released supported schema major installs and runs
> (current only before a second major exists; current and N-1 thereafter); unsigned, floating
> or incompatible packages are rejected.

Suite ID: PKG-001 (`package-matrix` slug), gate G1, requirements ARC-003, ARC-004, SPEC-002.
Candidate SHA: `653471d73f2352a77f2cf2ef2856f6f9e17873d1` (core `main`, "Adopt delivery
operating model: gates, task-ready and planning pin (#10)"), run from a clean worktree pinned
to that exact commit. All runs below are `localUnsigned`/informative per `--allow-unsigned`;
none is protected release evidence.

## What was rewritten vs. reused

Reused from salvage, structurally unchanged: the exact-pinning scan over every manifest field
(`dependencies`/`devDependencies`/`peerDependencies`/`optionalDependencies`), the
private/exact-version checks on every non-root package, the frozen-lockfile `npm ci` proof, and
the Northstar release-lock/required-packages provenance checks. None of that logic presupposes
a second spec major, so none of it needed to change.

Rewritten: the two touch points that presupposed major 2 —

1. **CLI contract.** `assert.equal(options.schema, "current,previous", ...)` became
   `assert.equal(options.schema, "released", ...)` to match the amended catalog command
   verbatim.
2. **Installable-majors assertion.** Salvage's `assert.ok(matrix.supported.length >= 2, ...)`
   treated a single supported major as a suite failure — under the amendment that is
   backwards, for the same reason SPEC-002's rewrite gave: a runtime that has genuinely
   released only one major and truthfully declares only that major installable is compliant,
   and forcing a fabricated second major to pass would itself be the violation. The rewrite
   branches on `previous`, computed from `matrix.supported` the same way SPEC-002 computes it
   from `SUPPORTED_SPEC_MAJORS`:
   - **One released major** (current state): asserts `matrix.previous === null` (fabrication
     check — a matrix that reports a previous major before one exists must be caught) and
     `supported` equals exactly `[current]`.
   - **Two or more released majors** (not yet reachable, written so it engages the moment it
     is): asserts both `current` and `previous` appear in `supported` — the N/N-1
     distribution ARC-004 actually requires once there is a previous major to distribute
     against.

Both branches read off the same `supported`/`current`/`previous` values derived from
`spec.compatibilityMatrix()`, so this is one assertion with two reachable outcomes, not a
suite plus a disabled stub — the two-majors path is inert today because `previous === null`,
not skipped.

Everything else in the salvage function — the exact-pin scan, the lockfile-freeze proof, and
the Northstar provenance checks — was ported byte-for-byte; only the schema-flag assertion and
the installable-majors assertion needed the amendment's rewrite.

## Mutants (dedicated throwaway worktree, removed after use)

Three mutants applied one at a time to a disposable `git worktree add ... 653471d... --detach`
of core, each reverted with `git checkout --` before the next was applied; `git status
--porcelain` was clean after each revert; the worktree was removed
(`git worktree remove --force`) after the last one. Each hits a distinct amended-oracle
behavior and fails for the asserted reason (verbatim from `measurements.error` in the
resulting evidence):

**Mutant 1 — the matrix fabricates a previous major.** `packages/spec/src/version.ts`,
`compatibilityMatrix()`: changed `sorted.length > 1 ? sorted[1] : null` to `... : 0`, so a
single-major runtime reports `previous: 0` instead of `previous: null`, without changing the
`supported` array. This is the same defect class SPEC-002's mutant 1 exercises, now caught
independently by PKG-001's own honesty check (ARC-004 pinning is a distinct requirement from
SPEC-002 negotiation).

```
the matrix must declare the previous major honestly

0 !== null
```

**Mutant 2 — a floating dependency range is accepted instead of rejected.**
`packages/composer/package.json`: changed `peerDependencies.react` from `"19.2.8"` to
`"^19.2.8"`.

```
every dependency and package version must be exactly pinned
+ [ { field: 'peerDependencies', issue: 'not an exact version', name: 'react',
      path: 'packages/composer/package.json', range: '^19.2.8' } ]
- []
```

**Mutant 3 — an inconsistent package version is accepted instead of rejected.**
`packages/composer/package.json`: changed `"version": "0.1.0"` to `"version": "0.1"`
(non-exact semver), simulating a package's own version drifting out of the pinned matrix.

```
every dependency and package version must be exactly pinned
+ [ { issue: 'package version must be exact semver', path: 'packages/composer/package.json' } ]
- []
```
